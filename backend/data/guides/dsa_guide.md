# Data Structures and Algorithms Preparation Guide

(Fictional sample guide written for the KRIT placement cell.)

## What companies ask

Almost every software role on campus tests data structures and algorithms in the online test and in at least one interview. Standard category companies mostly ask easy to medium problems on arrays, strings, hash maps and linked lists. Dream category companies add trees, graphs, heaps and dynamic programming.

## Topic order

Study in this order. Each topic builds on the previous one.

1. Arrays and strings: two pointers, sliding window, prefix sums.
2. Hash maps and sets: counting, lookups, anagram and duplicate problems.
3. Linked lists: reverse, find the middle, detect a cycle, merge two sorted lists.
4. Stacks and queues: valid parentheses, next greater element, queue using two stacks.
5. Binary search: on sorted arrays and on the answer.
6. Trees: traversals, height, lowest common ancestor, binary search tree checks.
7. Heaps: k-th largest, top k frequent, merge k sorted lists.
8. Graphs: BFS, DFS, connected components, shortest path.
9. Dynamic programming: climbing stairs, knapsack, longest common subsequence, longest increasing subsequence.

## Six-week plan

- **Week 1:** Arrays, strings and hash maps. Target 25 problems.
- **Week 2:** Linked lists, stacks and queues. Target 20 problems.
- **Week 3:** Binary search and trees. Target 20 problems.
- **Week 4:** Heaps and graphs. Target 15 problems.
- **Week 5:** Dynamic programming. Target 15 problems.
- **Week 6:** Mixed timed practice: two problems in 45 minutes every day, and two mock interviews.

## How to practise

- Solve on paper or in a plain editor at least twice a week. Interviews often have no autocomplete.
- For every problem, write the time and space complexity before you look at any solution.
- Keep an error log: one line per mistake, such as "forgot the empty input case". Read it before every test.
- Re-solve a problem you failed after three days without looking at the solution.

## In the interview

Repeat the problem in your own words, ask about input size and edge cases, state a brute-force idea first, then improve it. Dry-run your code on a small example before saying you are done. Interviewers give credit for a clear approach even when the code is incomplete.

## Common mistakes

- Memorising solutions instead of patterns.
- Skipping easy problems and then failing them under time pressure.
- Ignoring complexity analysis.
- Practising only in one language feature set and not knowing the standard library for maps, sets and heaps.
